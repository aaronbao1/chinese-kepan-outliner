# ingest — sources → input-text

**Input:** CBETA TEI-P5 XML from `github.com/cbeta-org/xml-p5`, one file per work (e.g. `T/T09/T09n0262.xml`), fetched per work from raw.githubusercontent.com pinned to release tag 2026R2 with sha256 checksums (R02, R04) — or other Unicode e-texts, plus a `role` tag (`root` | `commentary`) so the outliner knows which text is which.
**Output:** `InputText`, one per ingested text:
- the plain Unicode text, exactly CBETA's characters and punctuation;
- `structure.json`: a side-table of preserved structural markup (juan/pin boundaries, headings, any explicit division/mulu elements, verse groups, line/page refs like `T09n0262_p0001c05`) mapped to char offsets, so later stages can cite locations and the outliner can consume *explicit* structure;
- `apparatus.json`: a side-table of textual variants (lemma, readings, witness sigla, whether the note is Taishō's or CBETA's). PARTIAL (R02 F5/F22; the thread's 2026-09-21 upgrade to "VERIFIED, restricted to a Taishō-witness variorum" was returned to PARTIAL by the 2026-09-22 panel, so it is not applied here): CBETA encodes Taishō collation as stand-off TEI `app`/`lem`/`rdg` in `<back>` with a per-text `listWit`; across all 2,459 T files 94.32 % of 591,364 Taishō footnote ids have an `app` (≥ 94.38 % counting CBETA's letter-suffixed split anchors), the residue being Latin-script glosses, provenance/juan-boundary notes and 8,302 ids in variant syntax that are only partly classified — unencoded lemma variants lie between a confirmed non-zero floor and 1.40 % (symbol-form) or 2.86 % (all non-Latin residue), R02 G11. T0262: 945 `app` over 1,015 `orig` note elements = 1,004 ids, 743 matched, 261 residue; T1723: 2,260 `app`, 2,058 ids, 25 residue (R02 F21). Rule for the by-product: match apps by `#beg`+id or `n`, follow `corresp` for ＊ repeats, label `add`-anchored apps as 【CB】 readings, also match `#beg`+id+`[a-z]`, and report the residue by syntax class, flagging prose-form 「X本作Y」 notes. It remains a variorum over the witnesses Taishō collated (352 T files have only 【CB】【大】), not over editions Taishō never saw — whether that is enough for the variorum step of the Tibetan workflow (Agentic 1.0 §1e2) is open (R02 G14); see `docs/chinese-workflow-mapping.md` D2.

The coordinate system for every later location is the CBETA line reference plus char offset.

Rules: never normalize punctuation or variant characters silently; normalization is a separate, configured step with its config recorded alongside the output. OCR (Agentic 1.0 §1e1) is out of scope here: CBETA is already Unicode (VERIFIED, R02); non-CBETA material would be OCR'd upstream (dharmamitra.org/ocr also has a documented job-polling API, `POST /api-search/ocr/` with `model` gemini-mitra | bdrc-mitra | surya-mitra | auto — R05 F22, PARTIAL — but Chinese input and vertical Taishō layout are unattested and the upload is a gated call while terms are unconfirmed) and fed in as a Unicode e-text.

**What CBETA carries (R02, 2026-09-17).** Juan: `<milestone unit="juan"/>` + paired `<cb:juan fun="open|close">` holding `<cb:mulu type="卷"/>` and `<cb:jhead>`. 品: `<cb:div type="pin">` wrapping `<cb:mulu level="1" type="品">` before the printed `<head>`. `cb:mulu` is CBETA's own editorial table-of-contents layer with a documented type vocabulary (卷 經 序 處 會 地 品 分 論 跋 科判 附文 其他); pass `@type` and `@level` through verbatim, never hard-code. T09n0262 yields 7 卷 + 32 level-1 nodes (28 品, 3 序, 1 附文) + 1 level-2 序 under the 附文 branch (R02 F20, VERIFIED); T34n1723 yields 20 卷 + 28 品 + 10 untyped level-2 nodes that are per-juan continuation markers, to be emitted as `juan-marker`, not outline nodes (R02 F27, R04 F37). Corpus-wide (R02 pass 2, 2026-09-21, survey over all 5,017 files at tag 2026R2 — F16 VERIFIED; F15/F17/F18/F19 PARTIAL after the 2026-09-22 panel with every count reproduced): 科判-typed `mulu` exists in exactly 4 of 5,017 files (X11n0268 楞嚴經集註 2,611 nodes to level 28; P167n1573; D14n8842; G069n1977), none Taishō — when a file carries them the explicit tier already is a kēpàn; 39 of the 158 Taishō commentaries carry level ≥ 2 nodes (7 to depth ≥ 3); no Taishō sūtra file carries a 序分/正宗分/流通分 node — 分 in sūtras is the text's own section unit, a sibling of 品/會/經, so read the exegetical 三分 only when the label says so. CBETA Online's tree is the `works/toc?work=<id>` API JSON built from these inline elements (the bare `toc` route needs `q`), so there is no hidden outline dataset. Canonical locator = composed linehead `{TEI/@xml:id}_p{PPPP}{[a-g]}{LL}` (registers d–g occur in 822 lines), keyed on the `lb@n` value + release tag, never on the element; `lb`/`pb` value sets are identical between the 2018 archive and 2026R2 for 2,447 of 2,456 T files, the exceptions (added/removed markers, five renumbered columns in T08n0251/T40n1805, the T0220 `xml:id` merge) go into a migration list (R02 F18). Record `editorialDecl/punctuation` (新式標點 in 2,086 T files incl. both fixtures, 原書標點 in 373; AI 標點 / 基本句讀 outside T) and the `resp1` name per file in the normalization config — "CBETA's original punctuation" means CBETA's modern set for 新式標點 files (R02 F19). Keep `g` with its `charDecl` entry and `lg`/`l`/`caesura` boundaries (verse stanzas are chunk boundaries the sentence splitter cannot see). Side-table must keep: `lb` (n, ed), `pb` (n, xml:id), `milestone` juan, `cb:juan` (skip inside `note`/`lem`), `cb:mulu` (type, level, n, label) + enclosing `cb:div@type`, `jhead`/`head`, `<back>` apparatus + `listWit`, `note`, `g`. No Python parser exists (DILA ruby-cbeta is Ruby, CBReader cbxml.cpp is C++, cbeta-cli is Rust): write a thin lxml parser using `toc.rake` and `cbxml.cpp` as behavioural references. ## Implementation (M1a, 2026-09-27)

Modules: `lines.py` (line extractor, `python -m chinese_workflow.ingest.lines`), `text.py` (`InputText`, `load_input_text`), `structure.py` (`build_structure`, `normalization_config`), `run.py` (`run`, `parse_span`, CLI), `__main__.py`.

```
python -m chinese_workflow.ingest run SOURCE --role root|commentary --out DIR [--span FIRST..LAST] [--frozen TAG]
python -m chinese_workflow.ingest lines ...        # forwards to the line extractor CLI
```

`run(source, *, role, out_dir, span=None, frozen=None, guard=None)` (SOURCE = CBETA file id resolved under `data/raw/cbeta/`, or a path) writes:

| File | Content |
|---|---|
| `<id>.lines.jsonl` | the `ingest.lines` records of the span |
| `<id>.txt` | `InputText.text`: lines concatenated without separator, UTF-8, no trailing newline; its sha256 is `InputText.sha256` |
| `<id>.structure.json` | `structure/1`: `text_id, role, cbeta_release, title, punctuation, punctuation_resp, header_date, source, span{first,last}, length, sha256, lines[{linehead,start,length,juan}], elements[{kind,linehead,offset,char_start,attrs}]` |
| `normalization.config.json` | `{text_id, regime: "none", punctuation, punctuation_resp, gaiji_routes{route: n}, notes_policy, excluded_notes, renderings}` |

and returns `{text_id, sha256, paths, counts{lines, chars, elements{kind: n}, excluded_notes, gaiji}, split_guard}`.

Element kinds (`char_start` = `TextIndex.global_offset(linehead, offset)`, document order): `juan` (cb:juan open/close), `mulu` (type/level/n/label/div_type verbatim), `head`, `jhead` (the text stands at `char_start`), `verse` (a maximal run of `in_verse` lines, with `linehead_end`, `char_end`, `lines`), `note` (inline notes kept in the text, one element per line fragment; excluded notes with their full text, `in_text: false`), `caesura`, `gaiji` (ref and charDecl route), and `unclear` (not in the design's list: the `[?]` this pipeline renders for an empty `unclear`).

Decisions and limits:
- The split guard (`common.splits`, design §3) checks the span's lines before anything is written: a whole-file ingest of T34n1718 / T34n1723 needs `--frozen`.
- `normalization.config.json` has one fixed name per output directory, as the design names it; ingest the root and the commentary into separate directories (it carries `text_id`, so a mix-up is detectable).
- A `verse` element is a run of `in_verse` lines: two `lg` with no line between them form one run, and a line that opens an `lg` mid-line counts as verse from its start (none in T0262, T1666, T1753, T1703, whose `lg` all start on a new line). `juan` elements are the `cb:juan` marks; milestone juan numbers are in `lines[].juan`.
- Not built here: `apparatus.json` (the `<back>` app/lem/rdg side-table of the Input section above).
- Would help the segment stage (a change to `lines.py`, not made here): record `p` starts and `lg`/`l` offsets per line. Without `p` starts an unpunctuated dhāraṇī runs into the next paragraph's sentence (T0262 0058b19–c04).

Tests: `tests/unit/test_ingest_structure.py` (fixtures always; the whole-file T09n0262 check against `works-toc-T0262.json`, 7 卷 + 32 level-1 + 1 level-2 mulu, when `data/raw/` is present).
